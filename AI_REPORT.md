# Логи ИИ в разработке

## Запросы 2-го дня:

**Модель:** MiMo-v2.5

**Запрос:**

```md
Ты - ведущий Frontend-разработчик. В данном проекте будет постепенно разрабатываться веб-приложение Mini-shop - витрина интернет-магазина. Данные будут браться из открытого API DummyJSON (products). Верстка при помощи Material UI.

На сегодня необходимо выполнить следующие задачи:

1. Настроить React Router: маршруты / (каталог), /product/:id (товар), /cart (корзина).
2. Настроить тему дизайн-системы под проект (основной цвет, типографика) (не оставлять дефолтный вариант элементов).
3. Собрать общий layout на компонентах библиотеки: шапка с навигацией и иконкой корзины, контейнер контента, подвал.
4. Создать заглушки страниц и описать типы данных (Product и др.) по ответу API.
   Готово, когда: переходы между страницами работают, layout собран на компонентах дизайн-системы с настроенной темой. Дизайн должен быть красивым, современным, функциональным и отзывчивым.
```

**Комментарий:**

Модель отлично разбила логику приложения по разделам:

- `components` - реакт-компоненты
- `pages` - страницы для роутинга
- `theme` - темы веб-приложения
- `types` - описание типов компонентов

Реализованы все требования, маршрутизация работает корректно, типы данных описаны под API верно.

## Запросы 3-го дня

**Модель:** MiMo-v2.5

**Запрос:**

```md
Выполни следующие задачи на сегодня:

1. Сделать слой работы с API dummyJson products (функция запроса товаров) с обработкой загрузки и ошибки.
   Вся работа с API должна происходить в папке services, должна быть общая функция getResource, которая обращается к API и выдает JSON в случае корректной работы или ошибку.
2. Вынести запрос в кастомный хук с названием useProducts.
3. Отрендерить сетку карточек: картинка, название, цена, рейтинг.

Готово, когда: на главной видны реальные товары, корректно показываются состояния загрузки и ошибки.
```

**Комментарий:**

Для выполнения этого задания были созданы дополнительные папки для разделения логики:

- `hooks` - все кастомные хуки
- `services` - скрипты для работы с внешними сервисами

Вся основная логика отображения карточек описана в файле `pages/CatalogPage.tsx` с примением хука `useProducts`.
Данный хук хранит 3 параметра: массив продуктов, состояние загрузки, текст ошибки.
Он же и обращается к функции `getProducts`, чтобы произвести запрос к API.

Функция `getResource` вынесена в отдельный файл `api.ts`, чтобы поддерживать структурированность веб-приложения.
Она непосредственно обращается к API, а вызывается в `products.ts` в функции `getProducts`.

Ошибки обрабатываются корректно, загрузка страницы отображается правильно.

## Запросы 5-го дня

**Модель:** MiMo-v2.5

**Запрос:**

```md
Следующие задания:

1. Реализовать детальную страницу о товаре: запрос товара по id, полная информация о товаре
2. Добавить кнопку "В корзину" для каждой карточки в каталоге, а также в детальной странице о товаре (пока кнопка - просто заглушка)
```

**Комментарий:**

На данный момент, проведя ревью и рефакторинг, было выявлено несколько недочетов:

1. Флаг `cancelled` в хуках `useProducts.ts` и `useProduct.ts` спасает от обновления состояния, но не отменяет сам запрос к API.
2. Далеко не самое изящное решение для обработки события по клику на карточку.
3. Хуки `useProduct` и `useProducts` практически одинаковые и отличаются лишь парой строк кода, необходимо вынести их логику в общий хук.
4. При переходе на несуществующий продукт (например, /product/6436 или product/bjnbgjw) получаем ошибку вида: "Ошибка 404:".

## Запросы 9-го дня

**Модель:** MiMo-v2.5

**Запрос:**

```md
Необходимо реализовать логику корзины, для этого рассмотри следующие требования:

- Глобальное состояние корзины (Context API): добавление, удаление и изменение количества товаров в корзине.
- Внизу страницы корзины необходимо подсчитывать итоговую сумму товаров.
- Подключить кнопку "в корзину" у карточки в каталоге и детальной странице о товаре.

То есть пользователь может делать следующее:

1. Добавлять товар в корзину в каталоге товаров или на детальной странице о товаре.
2. Видеть итоговую сумму на странице корзины.
3. Добавлять несколько штук одного товара и менять его количество на странице корзины, а также полностью удалять товар из корзины.

Готово, когда: товары реально добавляются в корзину, сумма считается верно.
```

**Комментарий:**

Что удивило, ничего не сообщалось, как представить хранилище корзины, а модель все равно сделала именно так, как нужно в последующем задании - с использованием localStorage. Даже был реализован бейдж с количеством товаров возле значка корзины в шапке.

В целом, модель корректно поняла и реализовала запрос, однако не обошлось и без багов, которые пришлось исправлять:

1. Ввод количества без какой-либо строгой валидации. Допускается, что можно вписывать отрицательные числа и ноль, тогда товар просто пропадает из списка корзины.
2. Пункт 2 является следствием первого: нет никакой валидации по пределу количества товара, а значит, можно вписывать кучу цифр и получать, например, такой результат: $3.996e+21.

Поэтому было решено внести следующие исправления:

1. Убрать возможность ставить отрицательные числа и ноль (в таком случае значение становится 1).
2. При количестве товара более 999 единиц кнопка + блокируется, а число округляется до 999.

## Запросы 13-го дня

**Модель:** MiMo-v2.5

**Запрос:**

```md
Реализуем валидацию заказа и его финальное подтверждение.

1. Полная валидация с выводом ошибки под каждым полем.
2. Блокировка кнопки при невалидном вводе.
3. После корректной валидации и нажатия кнопки "Подтвердить заказ", необходимо переключиться на следующий этап "Подтверждение". В нем подтверждается заказ и корзина очищается (заказ оформлен).
   Готово, когда: работает полный путь «каталог → корзина → заказ → подтверждение».
```

**Комментарий:**

Модель корректно реализовала саму логику валидациии, но некорректо сделала отображение ошибок и логику кнопки подтверждения, усложнив подход с использованием useMemo.
Теперь при нажатии на поле ввода, а затем переключении в другую область, отображается ошибка под полем.

Был также еще один забавный баг, связанный с состоянием подтверждения заказа. После корректной валидации и нажатии на кнопку получаем заказ на 0$ и 0 товаров из-за того, что OrderConfirmation считывала товары/общую цену из контекста корзины, но onConfirm() очищал корзину с помощью useEffect, который запускал повторную визуализацию с пустыми данными. В данном случае просто необходимо было пробросить данные по заказу в OrderConfirmation.

## Итоговая рефлексия

### Лучшие промпты

Самыми эффективными оказались промпты с чёткой структурой и критериями готовности:

- **День 2** — подробное ТЗ с перечнем задач и фразой «Готово, когда: переходы между страницами работают, layout собран». Модель сразу выдала правильную структуру папок и полностью закрыла задачу.
- **День 9** — развёрнутое описание сценариев пользователя («То есть пользователь может делать следующее: 1… 2… 3…»). Модель не просто реализовала корзину, но и предсказала следующее задание, добавив localStorage и бейдж — без лишних указаний.

Ключевой паттерн: формулировка «Готово, когда: …» задаёт чёткий порог завершения и не даёт модели отклоняться от цели.

### Где ИИ помог идеально

- **Структура проекта** — модель с первого дня правильно разбила код на `components`, `pages`, `hooks`, `services`, `types`, `theme`. Это сэкономило время на рефакторинге архитектуры.
- **Типизация** — рутинная работа (типы для API, хуки, шаблоны компонентов) выполнялась быстро и без ошибок.
- **Валидация формы заказа** — логика проверок, блокировка кнопки, вывод ошибок под полями — всё реализовано корректно с первого раза.

### Где ИИ мешал

- **Неучтённые ограничения API** — на дне 7 модель подключила фильтр по категориям, но не учла, что эндпоинт `/products/category/{slug}` не поддерживает поиск `q=`. Пришлось переделывать на клиентскую фильтрацию.
- **Отсутствие валидации ввода** — на дне 9 модель допустила ввод отрицательных чисел, нуля и экстремально больших значений в поле количества товара. Результат — артефакты вроде `$3.996e+21`. Валидацию пришлось добавлять вручную.
- **Гонка состояний (race condition)** — на дне 13 `onConfirm()` очищал корзину через `useEffect`, а `OrderConfirmation` читала данные из того же контекста. Итог — экран подтверждения с 0$ и 0 товаров. Пришлось пробрасывать данные напрямую.
- **Визуальные дефекты** — на дне 15 модель не «видит» отрендеренную страницу, поэтому подобрала цвета футера, сливавшиеся с текстом. Такую проблему заметит только человек.

### Краткая рефлексия

ИИ — мощный инструмент для ускорения разработки: он быстро генерирует структуру, типы, компоненты и рутинную логику. Однако он склонен к «тихим» ошибкам: не проверяет ограничения внешних API, пропускает некоторые важные вещи, которые не указываются явным образом, и делает неоптимальные решения в некоторых случаях. Визуальные дефекты и проблемы с UX модель вообще не способна поймать без обратной связи от человека.

Вывод: ИИ лучше всего работает как «ускоритель» при чётком ТЗ с критериями готовности, а не как автономный разработчик. Ревью со стороны человека остаётся обязательным этапом — особенно на границах системы (API, ввод данных, визуал).
